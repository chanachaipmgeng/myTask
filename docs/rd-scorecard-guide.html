RND Development Index

ทีม Research & Development (R&D / RND) มีบทบาทหลักในการศึกษาเทคโนโลยีใหม่, วางมาตรฐานสถาปัตยกรรม (Architecture Baseline), สร้างงานต้นแบบ (POC / Spike), และลดความเสี่ยงทางเทคนิค (De-risking) ก่อนที่ทีม Implement จะนำไปสร้างเป็น Product จริง ดังนั้น สูตรคำนวณคะแนนของทีม R&D จึงไม่วัดเพียงแค่ความเร็ว แต่เน้นที่ "วินัยในการวิจัย (Spike Discipline)" และ "เกณฑ์ความสมบูรณ์เชิงวิศวกรรม (Definition of Done)"

RND Index = (0.40 × DoD Score) + (0.25 × Spike Quality) + (0.20 × Outcome Index) + (0.15 × Review/Reopen Quality)
40%
DoD Weighted Score
คะแนนใบงาน Feature/CR ที่ผ่านเกณฑ์ DoD 4 ด่าน (MR, Unit Test, Doc, Staging) และปิดสำเร็จ ถ่วงน้ำหนักตามขนาด Story Points
25%
Spike Quality Score
วินัยการทำ POC ภายในกรอบเวลา Timebox (0.5 หรือ 1.0 MD เท่านั้น) และต้องแตกงานลูก (Child Tasks) ที่ประเมิน Size ครบ
20%
Outcome Delivery
ร้อยละของ Actual MD ที่ส่งมอบคุณค่าจริงสำเร็จเทียบกับ Estimate MD ที่วางแผนไว้ในสปรินต์ (Capped สูงสุดที่ 100%)
15%
Review & Reopen
ความสะอาดของโค้ดและการทดสอบ วัดจากรอบตรวจ MR ไม่เกิน 2 รอบ และไม่มีประวัติการโดนตีกลับ (Zero Reopen)

เป้าหมายมาตรฐานและดัชนีสนับสนุน (Supporting Targets)

  • RND Index เป้าหมาย: ≥ 75 คะแนน (เกณฑ์มาตรฐาน), ≥ 85 คะแนน (เกณฑ์ดีเยี่ยม)
  • Spike Ratio ในกรอบมาตรฐาน: 15% ≤ Spike MD / Planned MD ≤ 40% (ต้องไม่ต่ำกว่า 15% เพื่อไม่ให้ขาดนวัตกรรม และไม่เกิน 40% เพื่อให้ยังมีเวลาส่งมอบคุณค่าหลัก)
  • Unplanned Ticket Ratio: ≤ 25% (สัดส่วนงานด่วน/งานแทรกนอกแผนไม่ควรเกิน 1.25 MD ต่อสัปดาห์)
  • Focus Time ต่อวัน: 1 Man-day (MD) = 6 ชั่วโมงทำงานมาตรฐาน

วงจรชีวิตใบงานและกลไกการตัดรอบส่งมอบที่เป็นธรรม (Fair Cutoff)

Lifecycle & SLA Mechanism

เพื่อป้องกันปัญหาคลาสสิกที่ "Dev ทำงานวิจัยเสร็จทันเวลา แต่ติดคิวรอ QA ทดสอบหรือรอฝั่ง Deploy จนวันปิดการ์ดเลย Due Date ทำให้ Dev โดนตัดคะแนน On-time" ระบบจึงนำ Fair Cutoff Rule มาบังคับใช้อย่างเป็นทางการ

1
Planning
สร้างการ์ดใน OpenProject ระบุ Track = RND, Estimate Time, ระบบล็อค firstDueOn อัตโนมัติ
2
Research & Dev
ลงมือวิจัย/เขียนโค้ด บันทึกเวลา actualHours, GitLab ซิงก์ commits และวัด commitSpanHours
3
Fair Cutoff ⭐
ย้ายเข้า Ready for QA ครั้งแรก ระบบสแตมป์ readyForQaAt และ ล็อคคะแนน On-time ของ Dev ทันที!
4
DoD Gate
ตรวจเช็คลิสต์ DoD 4 ข้อ (MR Review, Unit Test ≥ 80%, เอกสาร ADR, Staging Test)
5
Done & Score
การ์ดเข้า Done คำนวณ RND Index, คืนเครดิตรีวิว 10% ให้ผู้ตรวจ MR, บันทึก KPI Snapshot
ข้อตกลง Fair Cutoff: วันส่งมอบ (Dev Delivered On) จะถูกตัดทันทีที่ย้ายเข้า Ready for QA ครั้งแรก หากส่งมอบทันสัปดาห์ที่กำหนดใน firstDueOn วิศวกร R&D จะได้คะแนน On-time เต็ม 40 คะแนนทันที แม้ว่า QA จะใช้เวลาทดสอบอีกหลายวันหลังจากนั้นก็ตาม

กติกาเฉพาะสำหรับงานวิจัยแบบ Spike (Timebox Discipline)

งาน Spike แต่ละใบมีระบบคะแนนแบบ All-or-Nothing (100 คะแนน หรือ 0 คะแนน) โดยต้องผ่านเกณฑ์ทั้ง 4 ข้อ:

ด่านตรวจสอบ (Gate) เกณฑ์ที่ระบบบังคับ ผลหากไม่ผ่านเกณฑ์
1. Timebox Legal Limit Estimate MD ต้องเป็น 0.5 MD (3 ชม.) หรือ 1.0 MD (6 ชม.) เท่านั้น หากตั้งเป็น 2 MD หรือ 3 MD คะแนน Spike Quality จะเป็น 0 คะแนน ทันที
2. Execution within Timebox งานวิจัยต้องสรุปผลเสร็จสิ้นภายในกรอบเวลาที่ตั้งไว้ (inTimeBox = true) หากการทดลองบานปลายเกินกรอบเวลา คะแนนจะตกเป็น 0
3. Child Tickets Sizing เมื่อ Spike จบ ต้องแตกงานเป็น Story/Task ย่อยที่ประเมินขนาด Size (XS–XL) พร้อมทำต่อ Spike ที่ทำเสร็จแต่ไม่แตก Actionable Tickets ให้ทีมทำต่อ จะได้ 0 คะแนน
4. Closure Status ต้องปิดสถานะเป็น Done ในระบบ Spike ที่ค้างข้ามสปรินต์จะไม่ถูกนำมาคิดคะแนนคุณภาพ

Data Dictionary

3.1 กลุ่มฟิลด์ที่ระบบเก็บและคำนวณอัตโนมัติ (Automated Tracking)

ฟิลด์ในกลุ่มนี้วิศวกร R&D ไม่ต้องกรอกซ้ำซ้อน ระบบจะดึงและประมวลผลจาก OpenProject, GitLab API, และ Commit Webhooks โดยตรง:

ชื่อฟิลด์ในระบบ แหล่งข้อมูล คำอธิบายการทำงาน ผลกระทบต่อคะแนน R&D
opId OpenProject ID รหัส Work Package ในระบบจัดการงาน ใช้จับคู่ความถูกต้องของข้อมูลข้ามระบบ
type Type Field จำแนกประเภทงาน เช่น Spike, Feature, TechDebt แยกคิดสูตร Spike Quality vs DoD Weighted Score
track Custom Field ระบุสังกัดสายงาน เช่น RND หรือ RD สวิตช์เข้าสูตรคำนวณของ R&D Engine (40/25/20/15)
estimateMd Estimated Hours แปลงจากชม. เป็น Man-day โดยหารด้วย 6 ใช้ตรวจสอบ Timebox ของ Spike และคิด Accuracy
actualMd Spent Time Logged แปลงจากชั่วโมงที่ Log ในระบบ หารด้วย 6 คำนวณสัดส่วนความแม่นยำ (Actual / Estimate)
firstDueOn Due Date (Created) ระบบจับค่าวัน Due Date ครั้งแรกสุดแล้วล็อคทันที ใช้เป็นเส้นตายอ้างอิง On-time (ห้ามเลื่อนหนีคะแนน)
readyForQaAt Stage Logs เวลาประทับเมื่อการ์ดย้ายเข้า Ready for QA ครั้งแรก Fair Cutoff: ใช้คำนวณ Week Offset ส่งมอบของ Dev
reopenCount Status History นับจำนวนครั้งที่การ์ดถูกตีกลับจาก QA หรือ Review คิดคะแนน Reopen (20, 10, 0) และ Rework Rate
commitSpanHours GitLab Commits ระยะเวลาห่างจาก First Commit ถึง Last Commit ใช้ทำ 3-Way Time Audit ตรวจจับ Ghost-logging
reviewerCreditMd GitLab MR API ตรวจจับเมื่อวิศวกร R&D ไปกด Approve MR ให้เพื่อน คืนเครดิตเวลา 10% ของขนาด Estimate ของงานนั้น

3.2 กลุ่มฟิลด์ที่ทีม R&D หรือ Lead ต้องระบุหรือตรวจสอบ (Manual Input)

ชื่อฟิลด์ ใครเป็นผู้บันทึก เกณฑ์และแนวทางการระบุข้อมูล ผลกระทบต่อคะแนน R&D
isSpike Dev / Lead เลือก Type = Spike เมื่องานนั้นเป็นการศึกษาหรือ POC เปิดโหมดคำนวณ Spike Quality และ Spike Ratio
inTimeBox Dev / Lead ติ๊กยืนยันเมื่อสรุปผลการวิจัยได้ภายในกรอบเวลาที่ตกลงไว้ จำเป็นต่อการได้ 100 คะแนนเต็มของ Spike ใบนั้น
childTicketsSized Dev / Lead ติ๊กยืนยันเมื่อแตก Actionable Tasks พร้อมระบุ Size (XS–XL) จำเป็นต่อการได้ 100 คะแนนเต็มของ Spike ใบนั้น
dodPassed Lead / QA ผ่านเกณฑ์ 4 ด่าน (MR Review, Test ≥ 80%, Doc, Staging) หากไม่ผ่าน งาน Feature/CR ใบนั้นจะไม่ถูกคิดคะแนน DoD
varianceCode Dev / Lead ระบุสาเหตุเมื่อส่งช้า: REQ (สเปกเปลี่ยน), BLK (ติดบล็อค), ENV (แล็บล่ม) หากตรงกับ 3 รหัสดังกล่าว จะได้รับสิทธิ์ Exempt (คะแนนเต็ม)
isSplitEffort Lead / Dev ระบุสัดส่วนเมื่อทำงานวิจัยร่วมกัน เช่น นาย A 60%, นาย B 40% เฉลี่ยทั้งตัวหารโควตาและคะแนนส่งมอบตามสัดส่วนจริง
leaveDays Lead / HR ระบุวันลาพักร้อน/ลากิจของวิศวกรในรอบสัปดาห์ คำนวณ Dynamic Quota ปรับลดเป้าส่งมอบสุทธิลง

มิติตัวชี้วัดการประเมินผลและการแปลความหมาย (5 KPI Dimensions)

Evaluation & Insights

ข้อมูลและคะแนนที่บันทึกสามารถนำไปใช้ประเมินและสะท้อนทักษะของวิศวกรวิจัยและพัฒนาใน 5 มิติสำคัญ:

มิติการประเมิน ตัวชี้วัดที่ใช้ สัญญาณเตือนที่ต้องระวัง แนวทางการปรับปรุงและ Coaching
1. ความแม่นยำในการส่งมอบ (Delivery Predictability) - outcomeIndexPct (≥ 80%)
- weekOffset (≤ 0 wk) 		Outcome ต่ำกว่า 60% ต่อเนื่องหลายเดือน แสดงว่างานวิจัยขึ้นหิ้ง ไม่สามารถต่อยอดสู่ Production ได้จริง ปรับขอบเขตของ POC ให้กระชับขึ้น มุ่งเน้นแก้ Pain Point ของระบบ มากกว่าทำวิจัยเชิงทฤษฎี
2. วินัยการวิจัยนวัตกรรม (Research Agility) - spikeRatio (15%–40%)
- spikeQuality (≥ 85%) 		- Spike < 15%: ทีมหมดไฟ นวัตกรรมหยุดนิ่ง
- Spike > 40%: วิจัยฟุ้งซ่าน ไม่ส่งมอบคุณค่าหลัก 		จัดสรร Backlog ให้มีงาน Spike ประมาณ 1 ใน 4 ของเวลาทั้งหมด และคุม Timebox 3 ชม. หรือ 6 ชม. เคร่งครัด
3. คุณภาพเชิงวิศวกรรม (Engineering Rigor) - dodWeightedScore
- reworkRate (≤ 10%)
- Review Rounds (≤ 2.0) 		อัตรา Reopen สูงกว่า 20% หรือโดน Reject DoD บ่อย แสดงว่าโค้ดต้นแบบเปราะบาง ขาด Unit Test กำหนดให้ทำ Automated Test ในขั้น POC และจัดทำคู่มือสถาปัตยกรรม (ADR) ให้ครบถ้วนก่อนส่งมอบ
4. การทำงานร่วมกัน (Peer Collaboration) - reviewerCreditMd
- สถิติ Review ใน Time Audit 		วิศวกร Senior มีผลงานเขียนโค้ดเดี่ยวน้อยลงเพราะต้องสละเวลารีวิวสถาปัตยกรรมให้น้องในทีม ระบบบวกเครดิตเวลา 10% ให้ผู้รีวิวอัตโนมัติ ทำให้ Senior มีเวลาโควตารวมเพิ่มขึ้นอย่างเป็นธรรม
5. ความซื่อตรงของเวลา (3-Way Time Integrity) - Estimate vs Actual vs Commit Span Log เวลา 12 ชม. แต่วัด Commit Span จาก Git ได้เพียง 20 นาที (สัญญาณ Ghost-logging หรือ Over-commitment) ใช้ข้อมูลในหน้า /analytics/time-audit พูดคุยแบบ 1-on-1 เพื่อปรับ Work-Life Balance และแก้คอขวด

ภาพรวมการตรวจสอบเวลา 3 มิติ (3-Way Time Audit Concept)

ระบบ Time Audit ในหน้าจอที่ 23 (/analytics/time-audit) ช่วยให้หัวหน้าทีมและวิศวกรตรวจสอบความสมดุลของเวลา 3 แหล่งข้อมูล:

1. Estimate MD
เวลาที่วางแผนไว้ในสปรินต์
2. OpenProject Actual
เวลา Focus ที่วิศวกร Log จริง
3. GitLab Commit Span
ระยะเวลาที่โค้ดจริงบน Repository
สรุปคำแนะนำสำหรับวิศวกร R&D: ยึดมั่นในวินัย 5 ข้อ — (1) คุม Timebox ของ Spike ไม่เกิน 1 MD, (2) รักษาสัดส่วนงานวิจัย 20%–35%, (3) ย้ายเข้า Ready for QA ทันทีที่พร้อมตรวจเพื่อรับสิทธิ์ Fair Cutoff, (4) เช็คลิสต์ DoD ให้ผ่านรอบเดียว, และ (5) ระบุ Variance Code เสมอหากติดปัญหาภายนอก
